# Overall Themes

The comments point to several systemic risks rather than isolated typos:

1. **The test harness can produce misleading outcomes.**
   Many tests combine `set -e`, suppressed stderr, command substitutions, and aggressive teardown in ways that can cause raw aborts, false passes, false failures, or loss of diagnostic evidence.

2. **Destructive lifecycle operations are not validated strongly enough.**
   Workspace IDs, compose project names, volume names, paths, and fixture roots are sometimes derived or scraped without enough validation. This creates risk of operating on the wrong project/volume or destroying evidence while cleanup is still failing.

3. **Identity and state trust are brittle.**
   `identity/workspace-id.sh` is central to trust, path resolution, compose project naming, and state reuse, but the review found gaps in environment isolation, parsing strictness, path validation, temporary-file handling, permissions, and locale-dependent sanitization.

4. **Docker Compose generation and runtime behavior need tighter contracts.**
   Generated compose files can inherit injection risk; lifecycle commands may resolve identity metadata loosely; `docker compose up -d` may pull images by default even when the design claims startup never downloads.

5. **Build-context and image supply-chain hygiene is incomplete.**
   `.gitignore`, `.dockerignore`, and `Dockerfile` issues include unignored secrets/state, architecture-dependent pinning, overridable integrity inputs, mutable toolchain config, and stale comments about ownership/caching.

## 1. `tests/workspace-lifecycle.test.sh`

**Comment count:** 10
**Inferred severity:** High
**Core problem:** The lifecycle test suite has several correctness and safety issues that can mask failures, skip intended coverage, or destroy evidence during cleanup.

### Key Findings

#### 1. Missing preflight/SKIP guards for required tools

The tests do not reliably probe for required external tools or plugins, such as the Docker Compose plugin and `mise`/toolchain prerequisites.

This means hosts missing prerequisites may produce raw failures or aborts instead of a clean CI skip signal.

**Impact:**

- False-negative CI failures on unsupported hosts.
- Hard-to-distinguish infrastructure problem from product regression.

**Suggested fix:**

- Add explicit preflight checks:
  - `docker compose version`
  - `mise --version` or equivalent toolchain check
  - required plugin availability
- Emit a recognized SKIP status when prerequisites are absent.

---

#### 2. Command substitutions under `set -e` abort before reporting

Several assertions use command substitutions in ways that are not protected from nonzero exit statuses. Under `set -e`, a failing substitution can abort the script before the intended `ok`/`bad` reporting.

This includes cases where a missing or unexpected result is itself the intended test outcome.

**Impact:**

- Tests fail loudly for the wrong reason.
- Negative-path tests may never reach their intended assertion.

**Suggested fix:**

- Wrap command substitutions in explicit status handling:
  - Use `if out=$(cmd 2>&1); then ... else ... fi`
  - Or capture status with `|| status=$?`
  - Avoid bare command substitutions that can abort under `set -e`.

---

#### 3. Multi-step lifecycle chains are collapsed into one opaque status

Operations such as trust/marker/build/test/start are executed or treated as one combined status. This makes it impossible to tell whether the failure was in state setup, marker creation, build, test execution, or startup.

**Impact:**

- Poor failure attribution.
- Harder debugging.
- Cached results may mask whether tests actually executed.

**Suggested fix:**

- Split each lifecycle phase into its own guarded step.
- Record separate exit statuses and logs:
  - `trust`
  - `marker`
  - `build`
  - `test`
  - `start`
- Force non-cached test execution where persistence is being tested.

---

#### 4. Fallible lifecycle/snapshot commands lack explicit reporting

Some lifecycle or snapshot commands are run without explicit status checks or `ok`/`bad` reporting. A failure can abort the suite with no summary or mislead later assertions.

**Impact:**

- Suite termination without useful diagnostics.
- Later failures may be attributed to the wrong operation.

**Suggested fix:**

- Wrap all fallible commands.
- Capture stdout/stderr to log files.
- Check exit status and report the relevant log on failure.

---

#### 5. Identity values from generated compose files are not validated

Identity values extracted from generated compose files — such as name, project, or workspace ID — are not checked for being exactly one well-formed value.

If values are empty or multiline, paths and project names can collapse or become malformed.

**Impact:**

- False passes.
- Wrong volume/path/project derivation.
- Potential destructive operations against unintended targets.

**Suggested fix:**

- Require exactly one non-empty value.
- Validate against a conservative regex, e.g. compose-safe identifier chars only.
- Do not derive paths/volumes from unvalidated extracted values.

---

#### 6. Docker Compose `exec`/`run` assertions need safer invocation

Compose `exec`/`run` commands used for assertions should pass `-T` and construct commands safely with positional arguments or robust quoting.

**Impact:**

- TTY behavior can introduce CRLF or terminal artifacts.
- Injection risk if user-provided or derived values are not quoted.
- Empty output can produce misleading diagnostics.

**Suggested fix:**

- Use `docker compose exec -T ...`
- Pass commands as separate arguments rather than embedded shell strings.
- Avoid eval-like patterns.

---

#### 7. Advertised `remove-runtime` coverage is missing

The test header advertises a `remove-runtime` leg in the lifecycle journey, but the suite does not actually assert that path. `remove-runtime` is only invoked from cleanup with discarded stdout/stderr and `|| true`.

**Impact:**

- A regression in `remove-runtime` is invisible.
- Cleanup can succeed or fail without affecting test result.
- Volume/state removal behavior may not be tested.

**Suggested fix:**

- Add an explicit `remove-runtime` assertion.
- Capture and report stdout/stderr.
- Verify that only expected volumes/state are removed.
- Ensure failures in `remove-runtime` are surfaced.

---

#### 8. Teardown can destroy evidence while cleanup is still failing

Every teardown step is silenced and `|| true`-ed. Then cleanup unconditionally runs `rm -rf` on `$fx` and `$root`.

If `remove-runtime` or compose `down` fails, the test may report nothing while destroying directories that may still be referenced by running containers or leftover state.

**Impact:**

- Loss of diagnostic evidence.
- Potentially unsafe cleanup on partial failure.
- False sense of successful teardown.

**Suggested fix:**

- Do not unconditionally destroy state after failed teardown.
- Preserve `$fx` and `$root` when cleanup fails.
- Report cleanup failure clearly.
- Consider an artifact path or keep-on-failure mode.

---

#### 9. Generator/helper stderr is discarded

Generator and helper invocations discard stderr. Under `set -e`, this can make failures hard to diagnose and can cause later file/identity checks to be unreachable or misleading.

**Impact:**

- Real causes hidden.
- Failures appear later in confusing places.

**Suggested fix:**

- Capture stderr to logs.
- Check command status explicitly.
- Print the relevant log tail on failure.

---

#### 10. Pinned image tag is duplicated in test and product code

The test hard-codes `image="hestia-fixture-tools:2026-09-09"`, duplicating the pin in `workspace/workspace-compose.sh`. These can drift.

After a bump, a preflight image inspect may pass for the old tag or skip for the new tag, causing the real symptom to appear later as a confusing failure.

**Impact:**

- CI/local mismatch.
- Drift between test assumptions and generated compose.
- Misleading preflight behavior.

**Suggested fix:**

- Source the image tag from a single constant file.
- Or extract it from `workspace/workspace-compose.sh` in a safe, validated way.
- Add a regression test that prevents duplicated tag literals.

## 2. `tests/workspace-id.test.sh`

**Comment count:** 8
**Inferred severity:** High
**Core problem:** Workspace identity tests do not reliably distinguish success from malformed output, missing tools, or environment differences, and they discard evidence on failure.

### Key Findings

#### 1. Helpers do not validate successful non-empty fields

Test helpers for workspace-id do not distinguish:

- successful non-empty field
- failed command with empty output
- malformed multi-line output

Comparisons and negative assertions can pass vacuously or abort without diagnosis.

**Impact:**

- False passes.
- Broken tool can appear to satisfy expected failure.
- Empty output can match empty expectation accidentally.

**Suggested fix:**

- Introduce a strict helper that checks:
  - exit status
  - stdout/stderr separately
  - exactly one non-empty field
  - field format constraints

---

#### 2. No preflight for the tested script itself

There is no check that `$wid` exists and is executable. Current checks treat any nonzero status as the expected rejection.

If `identity/workspace-id.sh` is missing, non-executable, or fails at the top due to syntax error or missing `git`, the test may pass incorrectly.

**Impact:**

- Major false-positive risk.
- Environment/tooling problems can masquerade as product behavior.

**Suggested fix:**

- Add:
  - `[ -f "$wid" ]`
  - `[ -x "$wid" ]`
  - `bash -n "$wid"` or equivalent syntax check where appropriate
  - required external tool checks, e.g. `git`

---

#### 3. Failure contracts are asserted by human-readable prose only

The tests assert failure using UX copy such as `refusing to reuse` and `collision`. Those strings may be changed in future PRs even when behavior remains correct.

**Impact:**

- Brittle tests.
- Legitimate copy changes break tests.
- Actual contract may be under-specified.

**Suggested fix:**

- Assert stable exit codes.
- Assert machine-readable reason codes where available.
- Keep prose assertions as secondary, not primary, validation.

---

#### 4. Record format re-implemented with hand-written regex

The test parses the identity record format with its own regex instead of using the tool’s own canonical reported path. It also conflates different failure modes: missing file, malformed file, old record not rewritten, etc.

**Impact:**

- Test can drift from the real record contract.
- Diagnostics can be misleading.
- Missing file and rewritten old file may produce similar failure output.

**Suggested fix:**

- Use the tool’s reported fields or a shared parsing helper.
- Distinguish:

## 10. `Dockerfile`

**Comment count:** 7
**Inferred severity:** High
**Core problem:** The Dockerfile has significant issues around architecture pinning, supply-chain integrity, mutable toolchain trust, root-owned state, runtime behavior, and cache hygiene.

### Key Findings

#### 1. Base digest is pinned, but architecture is not; mise artifact assumes `linux-arm64`

The base image is pinned by OCI index digest, but `--platform` is not pinned. The mise artifact path is hard-coded to `linux-arm64`.

On an amd64 builder, BuildKit may resolve the index to the host platform. That can yield an amd64 rootfs with an arm64 binary path or binary.

**Impact:**

- Wrong architecture binary.
- Build succeeds only by accident on ARM hosts.
- CI on AMD64 may break unexpectedly.
- Digest pinning gives false confidence without platform pinning.

**Suggested fix:**

- Pin `--platform` explicitly if target architecture is fixed.
- Or support multiple architectures with per-platform URLs/checksums.
- Fail early on unsupported platform.
- Verify `uname -m` / target architecture before downloading artifact.

---

#### 2. Pinning inputs are overridable and can bypass integrity

`MISE_VERSION` and `MISE_SHA256` are build-time ARGs. A caller can override them with a malicious or unintended version and provide a self-consistent digest for that version.

Because the checksum is only compared against the URL supplied via build args, the intended integrity story is bypassed.

**Impact:**

- Supply-chain integrity is weaker than intended.
- Builds can silently use arbitrary mise tarballs.
- Pinned digest/version can be overridden without warning.

**Suggested fix:**

- Make pinned version/checksum constants in the Dockerfile, not overridable ARGs.
- If overrides are necessary, require an explicit opt-in and fail by default.
- Verify checksums against an external trusted checksum list, not only the provided URL.
- Use pinned digests for mise releases or an internal mirror.

---

#### 3. `MISE_DATA_DIR` and global config are dev-writable, not immutable

Mise state is placed under `/home/dev`, including:

- shims
- installs
- config
- trust state

The global `mise.toml` is also copied into a dev-controllable location.

**Impact:**

- Container compromise can mutate toolchain configuration.
- Trust boundaries are weaker than they appear.
- Runtime workspaces or code with dev-user access may alter toolchain behavior.

**Suggested fix:**

- Store immutable toolchain config in root-owned locations.
- Use `--trust` or pre-trust carefully.
- Verify global config integrity or mount it read-only.
- Consider read-only `/home/dev/.config/mise` or separate immutable tool layer.

---

#### 4. `MISE_DATA_DIR` is declared after a run that uses default root locations

`ENV MISE_DATA_DIR` is declared after a `RUN` step that invokes `mise --version`. That step runs as root using default data/config locations and creates dead root-owned mise state:

- `/root/.config/mise`
- `/root/.local/share/mise`

This state is not used by the `dev` runtime user.

**Impact:**

- Confusing extra layer contents.
- Dead config in image.
- Potential user confusion if running as root.
- Violates expectation that only `/home/dev` mise state is used.

**Suggested fix:**

- Declare `ENV MISE_DATA_DIR` before the version-check `RUN`.
- Or run version check with the target user/env.
- Clean any accidental root mise state if created.
